第一步 / 区分目标

1.1 单任务延迟与整体吞吐量

数组元素之间不存在数据依赖时，不同元素的计算可以并发执行。任务独立性是本例能够利用并行资源的前提。

01 · 问题

为什么单个任务完成较慢的处理器，仍可能更早完成整批任务？CPU 与 GPU 的资源配置差异应当用哪些性能指标解释？

02 · 背景

Latency-oriented

优化单个任务从开始到完成的时间。典型 CPU 会用复杂控制逻辑、较大的缓存和推测机制减少单线程停顿。

Throughput-oriented

优化单位时间完成的总工作量。典型 GPU 把更多预算交给并行算术与线程状态，以容纳大量并发工作。

三种并行性

ILP
一条指令流内，互不依赖的指令重叠执行。
TLP
多个线程或线程束并发推进。
DLP
同一种操作作用于许多数据元素。

本章数组计算的不同元素互不依赖，因而可以同时分配给多个执行资源。面积和功耗有限，使得每个执行资源的能力与可配置数量之间存在取舍。

数组计算中的三种并行性

同一个线程提前加载多个互不依赖的 x[i]，使独立指令重叠执行，是 ILP（指令级并行）。将不同 i 分配给不同线程，是 TLP（线程级并行）。对多个 x[i] 执行相同的乘加运算，体现 DLP（数据级并行）。三者可以同时存在。

控制逻辑与缓存：功能不同，目标互补

图中的“控制”指处理器的指令控制与调度逻辑，例如取指、译码、依赖检查、指令发射与分支预测。其作用是组织指令的执行。“缓存”指保存指令或数据副本的存储结构，其作用是利用局部性减少对较远存储层级的访问。两者属于不同功能类别。

控制逻辑：组织指令何时执行
例如，某条加载指令等待数据时，乱序调度逻辑可以选择操作数已就绪的独立指令执行。它改变指令的执行安排，并不直接缩短该次存储访问的服务时间。

缓存：提供所需指令或数据
例如，加载 x[i] 时若命中较近的缓存层级，通常能比访问较远层级更早获得数据。缓存命中缩短该次访问等待，但不负责选择下一条算术指令。

在同一条依赖链中的联系：对于 load x[i] → multiply，缓存访问结果影响 x[i] 何时就绪，进而影响依赖乘法何时具备执行条件。等待期间，调度逻辑可能发射独立的 z = a + b。数据返回后，相关就绪状态更新，乘法才成为可发射的候选指令。

本节将控制与缓存归入同一预算类别，以说明它们与算术资源之间的分配关系。复杂控制逻辑与较大的缓存都可能减少单线程停顿，并占用芯片面积与功耗预算；实际设计中，这两类资源可以独立配置，其容量和比例取决于工作负载与设计目标。

缓存控制器与指令调度逻辑

缓存自身也需要控制逻辑，用于处理命中判断、缺失请求、替换和写回等事务。因此“控制逻辑”是一个范围较广的词。本图将核心的指令控制与调度功能简称为“控制”，而“Cache”表示缓存子系统；这是一种功能示意，并非完整、互斥的晶体管面积分类。CPU 与 GPU 都包含控制逻辑和缓存。

从资源投入到性能：中间机制与成立条件

增加控制或缓存资源，并不会直接使一次加法运算更快。它们主要通过减少指令流中的停顿，或增加独立指令的交叠执行，影响任务完成时间。

1. 单线程时间取决于计算与未被覆盖的等待

对固定指令序列，执行时间可写为 T = 指令数 × 平均 CPI / 时钟频率。CPI 是平均每条指令所需的周期数，包含依赖、访存和控制流等因素造成的有效停顿；多条指令交叠执行时，平均 CPI 可以小于 1。讨论以下机制时，暂时固定指令数与频率。

  • 更大的缓存：如果新增容量保留了原本会被淘汰、随后又被使用的数据，缓存缺失可能减少，依赖这些数据的指令因而更早就绪。链条为：容量增加 → 部分缺失转为命中 → 有效访存等待减少 → 执行时间可能缩短。
  • 更大的乱序窗口：处理器可以在更大范围内发现独立指令，并将其安排在等待期间执行。链条为：候选指令范围扩大 → 可利用 ILP 增加 → 部分等待被覆盖 → 执行时间可能缩短。若窗口内仍是同一条依赖链，收益可能很小。
  • 更准确的分支预测：错误路径上的推测执行和恢复次数可能减少，有效执行周期随之减少。预测结构增加并不保证准确率提高，实际收益取决于程序的分支行为。

时间示例：某任务的简化执行过程包含 20 周期计算与 80 周期未被覆盖的访存等待，共 100 周期。若缓存改善使后者降为 20 周期，总时间变为 40 周期，而计算仍需 20 周期。两组数字仅说明等待对总时间的影响，不对应具体芯片。

2. 并行资源的减少来自预算约束

在工艺、总面积与功耗约束近似固定时，更多预算用于控制和缓存，意味着留给算术执行资源等其他部分的预算可能减少。本图将这部分取舍简化为算术方块数量减少。这是资源分配约束，不能理解为缓存会直接降低运算吞吐量。

在运算类型、频率与每通道执行能力固定的近似模型中，算术吞吐上限 = 通道数 × 每通道每周期操作数 × 频率。更多通道可以提高这一上限，但需要足够的独立任务、指令供给和数据带宽。只有一个串行任务时，增加通道通常无法利用全部新增资源。

3. 实际吞吐量还取决于利用率

以算术操作数为工作量单位，可用 实际吞吐量 ≈ 算术吞吐上限 × 有效利用率 理解二者的关系。假设每通道每周期最多执行 1 次操作：16 个通道若只有 25% 有效利用率，平均为 4 次操作 / 周期；8 个通道若达到 75%，平均为 6 次操作 / 周期。这说明较少的通道也可能产生更高的实际吞吐量。

控制与缓存投入可能减少单线程停顿，也可能提高整个处理器的有效利用率。因此，单线程性能与实际吞吐量并非必然反向变化。预算分配图只描述资源配置；单线程时间与实际吞吐量仍需结合工作负载分析。

增加投入但性能未改善的情况

数据原本已能放入缓存时，继续增加容量可能不减少缺失；更大的缓存也可能增加命中延迟。长依赖链限制乱序窗口能够利用的 ILP。内存带宽已饱和时，新增算术通道可能持续等待数据。实际设计还需考虑频率、布线和功耗的变化，不能从单一资源的增加推导性能必然提高。

04 · 核心内容提炼

  • Latency 衡量单任务完成时间，Throughput 衡量单位时间完成的工作量；较高吞吐量不要求每个任务的延迟都更低。
  • 控制与缓存可通过减少有效停顿改善执行时间；算术资源数量影响运算能力上限。资源投入不直接等于性能。
  • 实际收益受任务独立性、数据局部性、带宽及有效利用率约束。CPU 与 GPU 都利用多种并行性，区别在于设计重心。

第二步 / 分析停顿原因

1.2 执行资源可用性与指令就绪条件

乘法依赖 x[i] 的加载结果。执行资源空闲并不意味着存在满足发射条件的指令。

01 · 问题

当乘法单元空闲时，处理器为什么仍不能执行 y[i] = 2 × x[i] + 1？若计算资源已经存在，增加同类资源能否解决这个停顿？

02 · 背景

执行指令需要同时满足操作数、依赖关系和硬件资源等条件。这里重点讨论真实数据依赖：一条指令必须获得前序指令产生的值，才能计算正确结果。资源空闲只满足其中一个条件。

在上述链条中，加载结果未返回时，乘法的源操作数不可用；乘法未完成时，加法也无法获得其结果。同一时刻，另一条 z = a + b 若操作数已就绪且不依赖 x[i]，则可能具备执行条件。

03 · 底层逻辑与解决方式

停顿的直接原因是缺少满足执行条件的指令。处理器可以缩短条件尚未满足的时间，也可以在这段时间执行其他独立指令。控制路径未确定时，还可以通过预测与推测提前推进取指和执行。

访存等待：缓存缩短操作数获取时间

如果 x[i] 命中较近的缓存层级，加载通常更早完成，依赖乘法也更早就绪。缓存改善的是访问过程；若仍然缺失，等待可能继续存在。

数据依赖：乱序执行利用同线程的独立指令

调度逻辑记录指令的依赖与就绪状态。乘法等待期间，可将独立的 z = a + b 提前执行，结果仍按体系结构要求提交。乱序执行改变执行安排，不能使依赖 x[i] 的乘法绕过真实依赖。

线程内独立性不足：SMT 扩展指令来源

同一物理核心保存多个硬件线程的状态，从其他线程中选择符合条件的指令使用空闲资源。线程之间仍共享硬件，SMT 的收益取决于这些资源是否存在互补的空闲机会。

控制路径未确定：分支预测与推测执行

分支预测提供可能的下一取指位置，推测执行沿预测路径提前处理指令。预测正确时可减少等待分支解析的影响；预测错误时需要丢弃错误路径结果并恢复状态。它们的作用不同于缩短访存时间，也不消除真实数据依赖。

下方选项将各机制对应到数组计算中的具体执行条件。

乱序执行 · Out-of-Order Execution

当较早的指令等待数据时，处理器从窗口中挑选已就绪且无依赖的后续指令执行；提交通常仍保持程序顺序，以维护精确状态。

OoO 与 SMT 可以共同工作

OoO 增加指令执行安排的灵活性，SMT 增加指令的线程来源。二者可以同时存在，不是先使用 OoO、失败后才切换到 SMT；最终能否执行仍取决于依赖、就绪状态和共享资源。

04 · 核心内容提炼

  • 执行资源空闲是指令可执行的必要条件之一，操作数就绪与依赖满足同样重要。
  • Cache 缩短部分访问等待；OoO 用同线程独立指令覆盖等待；SMT 从其他硬件线程补充候选指令。
  • 分支预测与推测执行处理控制路径的不确定性。所有机制都有适用条件，其收益取决于程序能够提供的独立工作。

第三步 / 从通用原理推导执行组织

1.3 从独立指令到多线程执行

本节从程序中的独立工作出发，说明保存线程状态与成组发射的理由，为下一节的 GPU 调度机制建立前提。

01 · 问题

单个线程中的独立指令有限，而程序还包含大量互不依赖的任务时，硬件如何获得更多可执行工作？

02 · 背景

上述机制围绕同一个问题：当前指令等待时，还有哪些工作可以执行？OoO 在同一线程中寻找独立指令，SMT 将来源扩展到其他线程。下一步讨论的不是另一套依赖规则，而是当独立工作很多时，如何组织这些工作。

独立工作来自程序。对于数组计算，单个元素内部仍有“加载 → 乘法 → 加法”的依赖，但不同元素之间没有这种依赖。可以让多个线程分别处理不同元素：线程 T0 等待 x[0] 时，T1 仍可能发出自己的加载，或计算已经返回的数据。创建线程是在表达已有的独立性，并不能消除原有依赖。

03 · 底层逻辑与解决方式

交替推进需要保留状态。硬件若要在许多线程之间选择工作，就需要保留它们的数据和执行进度，使某个线程等待时，其他线程能够继续。这与 SMT 的基本思路相通；对于大量独立任务，面向吞吐量的设计更重视可同时保留的线程状态规模。

大量相同操作适合成组组织。数组线程通常执行相同操作、处理不同数据。硬件可以让一组线程共享共同指令的发射，以分摊控制开销，同时在不同组之间选择就绪工作。这样，讨论对象便从“一个线程中的候选指令”扩展到了“多个线程组提供的候选指令”。

在 NVIDIA GPU 中，这种线程执行组称为 Warp，承载其状态、调度与运算资源的硬件组织称为 SM。多个 Warp 可以驻留在同一 SM；具体组成与对应关系见附录 5.1及附5.2。

04 · 核心内容提炼

这里得到两个硬件需求：保存多组执行状态，以及从中选择就绪指令。下一节以 NVIDIA GPU 为具体实例，为这些组织引入名称，并观察它们如何覆盖等待。CPU 与 GPU 都可以利用线程级和数据级并行；这是设计侧重点的比较，不是二者的绝对划分。

第四步 / 扩大调度候选范围

1.4 驻留执行组之间的交叠执行

上一节由独立工作推导出“保存多组状态、选择就绪指令”的需求。本节以 NVIDIA GPU 为例，说明这种组织如何使不同工作的等待区间交叠。

01 · 问题

当单线程能够提供的独立指令不足以覆盖长延迟时，GPU 如何保持执行资源持续利用？增加线程数量为什么可能有帮助？

02 · 背景

在 NVIDIA 的术语中，共同组织指令执行的线程组称为 Warp，保存线程状态并提供调度与运算资源的物理单元称为 SM。当一组的状态及所需资源已保留在 SM 上，就称为驻留。因此，“驻留执行组”在本节具体指驻留的 Warp；这些名称对应的是前节已经引入的执行需求。

驻留仅说明资源已分配；该组的下一条指令仍须操作数就绪、满足依赖等条件，才能参与发射选择。以下时间线假设各组已经驻留，重点观察它们如何交替发射指令。线程如何组成 Block、如何分配到 SM，以及组内如何共同执行，分别在附录和 1.5 节展开。

03 · 底层逻辑与解决方式

1.4.1 两个 warp 的六周期示例

假设只有一个发射槽，每周期最多发射一条 warp 指令。W0、W1 均已驻留，各自执行“加载 → 依赖该加载的加法”。加载在周期 t 发出，数据在 t + 4 周期开始时可用。两个加载可同时处于未完成状态。本例忽略带宽竞争和其他指令。

W1 的加载在 W0 访存尚未完成时已经发出，两个操作的等待区间发生重叠。即使每周期仅发射一条指令，多条此前发射的操作仍可能同时在不同流水线或存储系统中进行。

该过程在 6 个周期中使用了 4 个发射槽。两个 warp 只能覆盖部分等待；若存在更多独立且就绪的 warp，周期 3～4 可能被其他指令使用。

1.4.2 更多线程为何不一定消除空档

调度逻辑跟踪指令依赖与资源状态。某组缺少操作数时，其他组只有在自己的下一条指令也符合条件时才可被选中。所有驻留组都等待数据或同步条件时，即使线程数量很大，也可能没有可发射指令。

增加 warp 数量扩大的是候选集合，而不是每周期的发射槽数。它不能缩短每一次访问，也不能突破存储带宽或算术流水线的容量。

1.4.3 固定依赖间隔的调度模型

上例区分加载与加法。下方实验进一步简化：每个 warp 有持续的待执行工作，每次发射后，其下一条指令都在 L 周期后才允许发射；没有任务完成与退出。它用于单独观察驻留数量与等待间隔的关系，不是数组程序的完整仿真。

每行是一个 warp，每列是一个周期。● 表示该周期发射，– 表示等待依赖，· 表示就绪但未被选择。空白表示尚未播放到该周期。利用率是已经发射的槽数除以已经观察的周期数，而不是完成的任务比例。

例如 L = 8 时，周期 1 发射的 W0 在周期 9 最早再次就绪。只有一个 warp 时，周期 2～8 没有候选；8 个初始就绪的 warp 则可以依次填入这些周期。W0 的间隔始终保持为 8 周期。

24 周期内发射槽利用率的计算

模型只有 1 个发射槽 / 周期，所有组初始就绪。L = 8 时，1、4、8 个 warp 分别发射 3、12、24 次，利用率为 12.5%、50%、100%。这一模型不模拟真实指令混合、带宽竞争或多个调度器。100% 仅指本例发射槽无空档，不代表 GPU 达到峰值性能。

实验对照：三个预设固定 L = 8。单组预设显示等待空档，四组预设显示部分覆盖，八组预设显示完全覆盖。“回到周期 0”可从初始状态单步查看；播放过程中每条说明对应一个发射决策。
发射槽利用率—
· 就绪未发射– 等待依赖● 发射

驻留 Warp 的上下文保存在 SM/CU 中，调度器每周期从符合条件的候选指令中选择一部分发射。可驻留数量受寄存器、共享内存、线程块与硬件上限共同约束。

04 · 核心内容提炼

  • 独立指令不足时，其他线程可以提供额外工作；这是从 CPU SMT 过渡到 GPU 多线程调度的概念联系。
  • 线程状态描述每个执行实例的进度与数据；驻留意味着相应状态及资源已保留在执行单元上，不意味着独占算术通道。
  • Warp 是线程组。Ready 表示指令符合选择条件，Issued 表示获得一次发射机会，发射不等于完成。
  • 交叠执行让其他组的工作占用部分等待区间，提高资源利用率；原组的延迟可以保持不变。
  • 候选组必须独立且就绪，收益还受驻留容量、发射能力与数据供给限制。
练习：等待数据的 Warp 是否仍然驻留？

等待数据的 Warp 仍可保持驻留。此时变化的是后续指令的就绪条件，W0 已分配的寄存器等状态仍保留。它可以同时处于“已驻留”和“等待依赖”的状态。

练习：驻留数量是否决定每周期发射数量？

驻留数量描述候选组的规模，每周期发射数量还受发射槽数和指令就绪情况限制。若只有一个发射槽，则每周期最多选择其中一组的一条指令；其余组可能等待依赖，也可能已经就绪但未被选中。

练习：交叠执行是否缩短单次加载延迟？

本模型中 W0 的加载延迟保持不变，性能改善来自 W1 的工作与 W0 的等待交叠。真实硬件中并发请求还可能造成资源竞争，因此隐藏延迟也不意味着单次访问延迟必然保持不变或下降。

成组发射可以分摊控制开销，但组内线程选择不同路径时会产生执行约束。下一节讨论共享指令与分支分歧的关系。 继续 →

第五步 / 理解成组执行

1.5 共享一条指令，处理不同数据

数组计算中的线程执行相同的乘加运算，各自处理不同的 i。共同发射指令能够分摊控制开销，适用于此类数据级并行。

01 · 问题

GPU 为何将大量线程成组发射？同一组线程选择不同分支时，共享指令的执行方式如何保持每个线程的程序语义？

02 · 背景

SIMD 与 SIMT 的语义关系

CPU SIMD：向量指令处理 [x0, x1, x2, x3] × 2。GPU SIMT：程序写单个线程的 x[i] × 2，机器将线程分组执行。SIMD 是 Single Instruction, Multiple Data；SIMT 是 Single Instruction, Multiple Threads。Lane 是执行通道，线程是软件身份。

加入 if (x[i] > 0) 后，组内线程可能选择不同路径。Active mask 指定当前路径哪些线程参与，其他线程暂不产生该指令的效果。

观察角度CPU SIMDGPU SIMT
程序员看到显式向量值与向量指令许多标量线程及其私有状态
硬件组织一条指令驱动多个 lane线程按 warp / wavefront 分组发射
控制流常用 mask / predicate分歧路径按 active mask 执行并再汇合

术语：warp 是 NVIDIA 对 32 个线程执行组的称呼；AMD 称 wavefront，宽度依架构与产品而异。SIMT 不意味着每个线程在每个周期都独立发射不同指令。

03 · 底层逻辑与解决方式

对于相同操作、不同数据，成组发射可以分摊指令控制开销。当组内存在不同路径时，机器为各路径确定活跃线程集合，使不属于当前路径的线程不产生该路径指令的效果。在本例的简化模型中，A 与 B 分别执行，随后继续共同路径。

实验问题：半数分歧与交错分歧是否需要不同数量的执行路径？模式切换会更新路径数与 lane-slot 利用率。本例 A、B 各需一条等成本指令，忽略分支与汇合开销。

if (lane_condition) { A(); } else { B(); }
路径 A active mask
路径 B active mask
串行路径数 1本例 lane-slot 利用率 100%

lane-slot 利用率与执行时间

16 个线程各执行一次操作，有效工作量为 16。两条等长路径共提供 2 × 16 = 32 个 lane-slot，因此利用率 50%。真实路径长度可能不同，编译器可能采用谓词化，程序也可能受其他瓶颈限制。现代 NVIDIA 的独立线程调度改变控制和同步细节，但不会消除成组发射的效率约束；依赖隐式 warp 同步的程序可能不再满足正确性要求。

04 · 核心内容提炼

  • SIMT 提供标量线程的编程语义，并以线程组共享指令发射；线程与物理 lane 属于不同概念。
  • 组内路径不一致产生分歧；不同 warp 分别执行不同路径，不构成组内分歧。
  • Active mask 保持各线程的执行语义。分歧可能降低有效 lane 利用率，但对总耗时的影响取决于路径长度、编译结果及其他瓶颈。

第六步 / 用需求解释结构

1.6 执行机制对应的 GPU 硬件结构

SM（Streaming Multiprocessor）是 NVIDIA 的片上执行单元组织，包含线程状态、调度与执行等资源。AMD 的 CU 是相关硬件组织概念，内部结构并非一一对应。

01 · 问题

支持大量驻留线程、就绪组调度和成组执行，需要哪些硬件资源？Grid、Block、Warp 与 SM 分别处于什么层次？

02 · 背景

Kernel 是 GPU 上执行的函数；一次 launch 创建 grid，其中包含多个线程块。Block 定义一组协作线程，warp 是 NVIDIA 的线程执行组，SM 则是承载线程状态、调度与执行资源的硬件组织。AMD 的相关软件和硬件术语包括 work-group、wavefront 与 CU，具体组织依架构而异。

这些概念分别描述任务组织、执行分组与物理资源，因此不是逐层包含的同一种“核心”。

03 · 底层逻辑与解决方式

硬件资源与执行需求的对应关系

寄存器
保存 resident 线程状态；容量有限，所以不能无限驻留。
调度器
从 ready 组选择指令发射，覆盖其他组的等待。
执行通道
让活跃线程对不同数据执行共同的算术操作。
共享内存 / L1
提供片上数据存储。共享内存由程序显式管理，cache 通常由硬件管理，语义不同。
L2 / 显存
向执行单元供应数据。带宽影响总供给能力，延迟影响单次访问等待；增加线程数量无法突破带宽上限。

硬件将线程块分配到具有足够资源的执行单元。块中的线程被分为执行组，其状态占用片上资源；调度器选择就绪指令，执行通道处理活跃线程的数据，存储层次供应所需操作数。

04 · 核心内容提炼

  • Grid 与 Block 组织软件任务，warp 组织线程执行，SM/CU 提供硬件资源；逻辑线程数量不等于物理执行通道数量。
  • 寄存器支持驻留状态，调度器选择就绪工作，算术通道完成操作，缓存与显存提供数据。各资源共同决定性能。
  • GPU 的吞吐优势要求可利用的独立工作和充分的数据供应；线程数量本身不是性能保证。

本章结论

CPU 通常侧重降低单线程执行延迟；GPU 通常通过调度其他驻留且就绪的线程束，覆盖部分线程的等待时间，提高执行资源利用率与整体吞吐量。

线程、执行组织与硬件资源

附录 1：线程与执行状态

考虑一个没有线程间通信的任务：对 64 个数组元素分别加 1。程序只写一次 kernel，但每个线程使用自己的索引 i 和数据，形成不同的执行实例。

// CUDA 示例：每个线程计算一个元素
__global__ void add_one(const float* x, float* y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < 64) y[i] = x[i] + 1;
}
add_one<<<1, 64>>>(x, y);  // 1 个 Block，每块 64 个线程

blockIdx.x 是块编号，blockDim.x 是每块线程数，threadIdx.x 是块内线程编号。这里创建的是 64 次逻辑执行，不是 64 套运算硬件。

线程 T0 的状态
i = 0
读取 x[0]，写入 y[0]

线程 T1 的状态
i = 1
读取 x[1]，写入 y[1]

附1.1 线程在硬件中的表示

这次启动不会在 GPU 内存中创建 64 个普通的 Thread 对象。线程由一组执行状态表示，这些状态分布在寄存器文件和控制结构中，并不要求集中存放为一个对象。SM 接收工作后，才为相应线程分配执行所需的片上资源。

线程身份
块编号、块内编号等硬件提供的索引信息，使各线程能够计算自己处理的元素位置。
数据状态
当前操作数和中间结果保存在编译器分配的寄存器等存储位置中。
执行进度
程序计数器等控制状态记录后续执行位置；现代 NVIDIA GPU 支持每线程执行状态。
参与与等待状态
活跃掩码标记一次指令中参与的线程；依赖跟踪等结构帮助判断指令能否发射。这些信息并非全部按线程独立保存，也会按 Warp 等粒度组织。

例如，T7 已加载 x[7] = 20，下一步需要加 1。即使它暂时没有使用运算单元，数值 20 和继续执行所需的状态仍可保留。获得发射机会后，数据被送入运算通道，结果 21 随后写回；同一通道之后可以服务其他线程。

寄存器和控制结构保存“线程执行到哪里、已有何种数据”；运算单元负责处理这些数据。线程持续存在，不要求它持续占用加法器。这也是后文“驻留”的基础。

源码变量与物理寄存器不是一一对应：编译器可能消除变量、复用寄存器或将部分数据放入内存。这里描述执行状态的类别，不是具体芯片的寄存器布局。参考：CUDA 硬件多线程、独立线程调度。

与 CPU 软件线程、SMT 硬件线程的关系

CPU 软件线程通常由操作系统安排到逻辑处理器上；CUDA 线程随 kernel 启动创建，由 GPU 按 Block 和 Warp 组织执行。SMT 硬件线程指 CPU 提供的一套体系结构状态，并不是操作系统管理的软件线程本身。三者都涉及执行状态，但调度层次不同。

附录 2：Block 与 Warp 的分工

即使上面的 64 个线程完全独立，它们也必须属于 Block。Block 是 GPU 分配工作的单位，同时提供块内协作能力。普通 Block 被整体分配到一个 SM；SM 是承载线程状态、调度器与运算电路的硬件组织。不同 Block 可独立安排到可用资源上，不保证同时执行或按编号执行。

附2.1 Warp 的作用

线程需要不同操作时的执行方式，以及 SIMT 与算法复杂度的关系，见附录 12.2：算法复杂度与指令执行方式。

共同指令如何连接到多路运算硬件，见图 附3-1：一条加法指令与四路独立数据。

Block 确定一批工作的成员及协作范围，但硬件还需要决定每次如何向其中的线程发射指令。若各线程分别组织指令执行，会重复处理许多相同的操作；共享共同指令的发射，则可以把控制开销分摊到多份数据运算上。

也可以设想整个 Block 一起推进，但这会将程序配置的工作组大小与共同执行的范围绑定。引入 Warp 后，二者可以分开：例如一个 128 线程 Block 分为四个 Warp，各组可有不同进度。一组的指令等待数据时，另一组的就绪指令可能获得发射机会，无需整个 Block 始终同时推进。

Block 的大小服务于工作组织；Warp 的宽度服务于成组执行。Warp 在共享指令控制与保留组间调度灵活性之间提供一种组织方式。32 是 NVIDIA 的设计选择，并不是所有 GPU 必须采用的宽度。

自测：两个 Block 的结果最终要汇总，是否必须改成一个 Block？

不必。可以先让两个 Block 分别产生部分结果，再启动后续 kernel 汇总。最终属于同一个算法结果，不意味着必须属于同一块内协作范围。

附录 3：成组执行与硬件多线程

附3.1 共同指令与运算通道

指令与数据经过不同的线路。示意指令 ADD R2, R0, R1 指定“读取 R0、R1，相加后写入 R2”，并不包含具体的数值。同样的寄存器名称，在不同线程中代表各自的逻辑寄存器状态。

下图采用四个线程、四个加法通道的教学模型：同一指令提供操作控制，各线程分别提供数据。真实 NVIDIA Warp 包含 32 个线程。

控制信号可以通过布线和缓冲电路分发给多个接收端；数据输入则分别连接到各通道。因而，共享一条指令仍能保留多份数据的运算能力，并不要求所有数据依次经过同一个加法器。

图示省略流水线、寄存器分银行和操作数收集等细节，不是具体 GPU 的布线图。Warp 的 32 个线程可能分多拍处理；一条指令既不等于一次标量运算，也不保证一个周期完成。反过来，两个线程先后使用同一个加法器，也不能据此判断它们属于同一 Warp。

参考：CUDA 指南：SIMT、NVIDIA 操作数供给研究。

附3.2 Block、Warp 与 SMT 的关系

Block 与 Warp 不能简单对应“数据模型”和“控制模型”。Block 同时涉及工作分配、共享内存和同步控制；Warp 则组织共同指令对各线程数据的执行。不同 Block 可以访问同一份全局数据，同一 Block 内也可以处理互不相关的数据，因此 Block 不直接规定全局数据的划分或归属。

附录 4：线程配置、编号与设计依据

附4.1 可配置的 Block 与固定的 Warp

开发者知道算法希望如何组织工作，因此 CUDA 允许程序在硬件限制内配置 Block 的数量、大小和形状。Warp 则采用架构规定的执行分组规则：程序配置 Block 后，Warp 的成员随之确定，不能另行任意指定宽度或拼接成员。

kernel<<<2, 64>>>(...);  // 2 个 Block，每块 64 个线程

B0：W0 = 块内线程 0～31；W1 = 块内线程 32～63
B1：W0 = 块内线程 0～31；W1 = 块内线程 32～63

程序可以计算 Warp 编号，再给不同 Warp 安排不同工作，也可以使用组内交换、投票或同步操作。这是在利用已有分组，而非重新定义分组。Cooperative Groups 创建的软件协作子组同样不会改变硬件 Warp 的宽度与成员。

两者分开配置的理由是：算法的工作组大小需要灵活，而调度、活跃掩码及操作数供给等机制需要明确的执行单位。固定 Warp 规则提供了稳定的组织基础；这是一种架构选择，不表示可变分组在技术上不可能。

附4.2 Warp 的编号与划分规则

NVIDIA 按每个 Block 内的线性线程编号，从 0 开始，每连续 32 个线程划为一个 Warp，不跨 Block。编号由线程坐标决定，不由数据地址、分支路径或当前任务决定。

// 将块内坐标线性化：x 最快变化，其次 y，最后 z
tid = threadIdx.x
    + blockDim.x * threadIdx.y
    + blockDim.x * blockDim.y * threadIdx.z;

warp_id = tid / 32;  // 整数除法，得到块内 Warp 编号
lane_id = tid % 32;  // Warp 内位置，范围 0～31

附4.3 编号约定与设计依据

规则是确定的，最优性不是定理。CUDA 明确规定 Warp 宽度及线程线性化方式，但这不意味着数学理论证明了“32 个线程、连续分组、x 优先”是唯一最优方案。以下是理解这些选择的工程分析，而非对具体芯片设计历史的断言。

  • 固定宽度：便于围绕稳定的组内位置设计掩码、调度和组内通信。更宽的组可分摊控制开销，但也可能在分支不一致或工作不足时留下更多不参与的位置；收益取决于工作负载与实现。
  • 连续编号：组号和组内位置可直接由除法、取余求出；对非负编号，除以 32 等价于右移 5 位，取余等价于保留低 5 位。这使映射易于计算和预测，不代表硬件不存在其他映射或状态管理。
  • x 优先：这是坐标线性化约定，不是物理定律。程序若让相邻编号访问相邻地址，可能有利于内存访问合并；编号连续本身不保证地址连续或最佳访存效率。

程序配置工作组，硬件按架构规则形成执行组，程序再根据已知规则安排工作与数据。规则可以被利用，但不能把软件子组、数据划分或物理加法器数量当作 Warp 的定义。

参考：CUDA 指南：线程编号与 SIMT、Cooperative Groups、Intel SMT 资源共享说明。

附录 5：SM 的组成与资源分配

附5.1 SM 的主要组成

SM（Streaming Multiprocessor，流式多处理器）是 NVIDIA GPU 中承载线程执行的硬件组织。一个 GPU 包含多个 SM；每个 SM 都具备保存状态、选择指令和执行运算所需的资源，而不只是一个加法器。

这里的硬件名称是 CUDA Core，不宜简称为 CUDA。CUDA 本身是 NVIDIA 的并行计算平台与编程模型；CUDA Toolkit 则提供编译器、运行时库及开发工具。CUDA 与 SM 分别属于编程平台和硬件组织，不能作为同类部件比较。

附5.2 Warp 与 SM 的关系

Warp 是 32 个逻辑线程的执行分组，SM 是保存这些线程状态并执行指令的物理硬件。普通执行中，一个 Warp 的线程在同一 SM 上执行；一个 SM 可以同时驻留多个 Warp。

例如 B0/W0 的下一条指令等待加载结果时，其寄存器状态仍然保留；若同一调度器管理的另一 Warp 有就绪指令，就可能获得发射机会。不同调度器和流水线也可能并行工作，所以“一个 SM 承载多个 Warp”既不表示所有 Warp 同时发射，也不表示整个 SM 每次只能推进一个 Warp。

Warp 数量描述当前承载的逻辑工作，执行单元数量描述物理计算资源。增加驻留 Warp 能扩大候选指令来源，却不会增加 SM 或算术通道；驻留上限还受寄存器、共享内存和硬件限制约束。参考：CUDA：SIMT 与硬件多线程。

附5.3 Block 在 SM 上的分配

普通 CUDA Block 被整体分配到一个资源足够的 SM，其 Warp 在该 SM 上执行。分配更多工作不会产生新的 SM。

下例使用两个 SM，并假设每个 SM 最多同时驻留一个 Block。一种可能的分配是 B0 → SM 0、B1 → SM 1，而 B2、B3 等待资源。每个 SM 内的粗框表示硬件边界，内部细框表示当前驻留的逻辑工作。

切换到另一个已驻留 Warp 时，其寄存器值仍保留在已分配的位置，无需每次从内存重新装入整套上下文。驻留数量受寄存器、共享内存和硬件上限限制；真实 SM 可以同时驻留多个 Block，本例的单块容量仅用于说明分配过程。

附5.4 执行资源的共享与复用

线程数量与 SM 数量的关系

一个含 64 个线程的 Block 可以分配给一个 SM，其中两个 Warp 共享该 SM 的执行资源。线程数量描述逻辑工作规模，SM 数量描述物理硬件规模，二者没有一一对应关系。

附录 6：驻留、状态保留与调度

附6.1 驻留执行组：状态已保留的线程组

执行组是一组共同组织指令执行的逻辑线程，本节以 NVIDIA 的 Warp 为例。它不是 Block 与 SM 之间新增的一层：一个 Block 分为若干 Warp，SM 则是提供调度、寄存器和运算资源的物理执行单元。

驻留（resident）表示该组已获得相应的片上资源，其线程寄存器值、执行进度等上下文保留在所在 SM 上。这里保留的是继续执行所需的状态，不表示程序要访问的全部数据都已进入缓存，也不表示该组正在使用算术单元。

例如，同一 SM 上的 W0 正在等待加载结果，W1 的下一条指令已就绪。两组都可以处于驻留状态，但此时只有 W1 的这条指令具备发射条件：

同一 SM 上的驻留组
W0：状态保留 · 等待数据 → 依赖该数据的指令暂不能发射
W1：状态保留 · 指令就绪 → 可以参与调度选择
尚未分配到 SM 的 Block：不在该 SM 的驻留集合中

调度器选择 W1 时，W0 的状态仍保留在片上；因此，在已驻留 Warp 之间选择指令，无需每次从内存重新装入整套线程上下文。这为交叠执行提供了条件。寄存器容量、块级共享内存用量及硬件上限限制了可驻留的组数。

驻留描述“状态与资源已经就位”，就绪描述“下一条指令符合执行条件”，发射描述“这次被调度器选中”。增加驻留组扩大了指令来源，但不保证存在更多就绪指令。

参考：CUDA 编程指南：硬件多线程与片上上下文。以下说明状态保留方式与调度条件。

附6.2 状态保留与操作系统上下文切换

普通驻留 Warp 调度中，多组上下文已经同时保留在 SM 上。选择另一组的指令，通常无需先把旧组的上下文写入显存，再装入新组。这里的“保留”是持续占用已分配的存储位置，而不是每次切换都执行保存操作。

寄存器文件本身就是存储阵列。选择 W1 时，硬件读取属于 W1 的操作数并将结果写回对应位置；W0 的值仍保留，不会因运算通道改为服务 W1 而被覆盖。这里描述逻辑归属，不假定物理布局是每个 Warp 一块连续区域。

  1. W0 发射加载：硬件跟踪请求归属和后续依赖，其依赖加法等待。
  2. W1 发射就绪指令：执行单元使用 W1 的数据，W0 的状态仍在片上。
  3. W0 的数据返回：更新目的数据及依赖状态，满足条件的后续指令重新参与调度。

容量是这种机制的代价。寄存器和共享内存有限，每线程或每块用量增加可能减少可同时驻留的工作量。因此，已创建的线程不一定都已经驻留；已经驻留也不表示就绪或正在执行。

上述范围是正常的驻留 Warp 调度。寄存器溢出到内存、GPU 任务抢占和进程级上下文切换属于其他机制，不应由此推断所有切换都没有成本。参考：CUDA 硬件多线程、Nsight 调度与依赖跟踪。

附6.3 驻留、就绪、发射与完成

Resident
上下文及所需资源已经驻留。这描述资源占用；等待数据的 warp 仍然可以是 resident。
Ready
下一条候选指令满足当前的依赖与资源条件，可以参与选择。Ready 不保证本周期被选中。
Issued
调度器已将所选指令发往相应执行流水线。这是一次调度事件，不等于指令已经完成。
完成
该指令的相应操作已完成。以加载为例，数据返回后，依赖它的后续指令才可能就绪；这仍不等于整个线程完成。

驻留描述资源分配情况，就绪描述指令的执行条件，发射描述当前周期的调度结果。这些概念从不同角度描述执行过程：一个 Warp 可以已经驻留，但其下一条指令仍在等待操作数。
