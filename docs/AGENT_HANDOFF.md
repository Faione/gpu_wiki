## 4. 用户反复追问的理解难点

这些问题解释了当前内容为何如此组织。已添加说明不代表用户已确认掌握。

### 控制、缓存与性能之间的因果关系

用户能从图中看到“控制与缓存投入倾向”与“单线程响应”“并行吞吐潜力”的关联，但不理解底层原因。

当前教学重点：控制逻辑组织指令，缓存影响指令或数据的供应；二者功能不同，但可能共同减少有效停顿。固定预算下增加某类资源可能减少其他资源数量；实际性能仍取决于利用率、工作负载和数据供给。不能把预算分配图直接当作性能预测。

### 执行资源空闲与指令可执行的区别

用户要求对“执行资源可用性与指令就绪条件”重组逻辑。当前以 `load → multiply → add → store` 数据依赖链说明：运算单元空闲不等于操作数就绪，再由此引出 Cache、OoO、SMT 和控制流推测机制。

### 从线程到 SM，以及驻留组交叠执行

用户认为这里相比前文存在概念跳跃，因此已拆解为：独立线程 → 线程状态 → Block / Warp 分组 → SM 上的驻留 → 共享执行资源 → 驻留、就绪、发射、完成的区别 → 多组等待区间交叠。

### 为什么既有 Block 又有 Warp

用户不只需要划分规则，还需要解释划分的作用：

- Block 对应局部协作、共享内存、块级同步，以及工作分配和资源占用。
- Warp 对应共同指令的成组执行，能够分摊控制与发射开销。
- 用户了解 NUMA，可以借助局部性说明协作组织；但 NUMA 节点是硬件拓扑概念，Block 是程序工作组，不能建立一一对应。
- 用户常将 Warp 写作“wrap”；正文统一使用 Warp / warp，不必反复纠正拼写。

### SIMD、SIMT 与 Warp

用户最近明确表示“能够理解 Block，但对于 Warp 仍不清楚”。为此新增副页，从标量指令、SIMD lane、SIMT 线程语义过渡到 Warp 和活跃掩码。

最重要的解释是：**共同指令不要求共同数据；每个线程仍使用自己的操作数和寄存器状态。**

## 6. 技术准确性与模型说明

以下是项目已经确立的解释口径。后续新增硬件细节仍需核对官方资料。

- 区分通用 GPU 原理、NVIDIA CUDA 术语及具体架构行为；不要把 NVIDIA Warp 宽度推广到所有 GPU。
- 区分逻辑线程、执行分组与物理硬件。Warp 的 32 个线程不能等同于 32 个独立 CPU 核心，也不能据此断言一条指令一个周期完成。
- 区分 resident、ready、issued、completed；发射不等于完成。
- 延迟隐藏主要减少等待对资源利用率的影响，不意味着某次存储访问本身变快。
- 共同指令作用于各线程自己的数据；分支分歧不会重新划分 Warp 成员。
- 不假定现代 GPU 的同一 Warp 内线程始终隐式同步；线程通信需要相应同步机制。
- Block 取 32 的倍数、增加 Warp 数量或提高驻留数量，都不自动保证性能更好。
- 图中的简化数量、周期、发射槽和布局应明确标为教学模型。

具体实验约定：

- 主页面预算图固定 42 个示意预算单元，不是面积、功耗或性能实测。
- 调度实验采用 24 周期、单发射槽、固定依赖间隔 L 的模型；在 t 发射后，下一条最早 t + L 就绪。没有任务完成退出，不是完整数组程序仿真。
- 分支实验采用简化的等成本路径；lane-slot 利用率不能直接换算成真实运行时间。
- 副页将发射与结果完成合并为一个可视步骤，假设操作数与执行资源已就绪；SIMD 实验只统计加法指令，不是周期对比。
