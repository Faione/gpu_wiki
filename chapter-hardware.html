第二章 · 硬件如何完成计算

计算、存储与数据搬运

本章用一条数据流组织硬件知识：从设备内存取数 → 在片上复用 → 计算 → 写出结果。每节回答一个算子优化问题；电路与型号规格按需查阅附录。

以 NVIDIA GPU 上的常见 CUDA 执行模型为例。图中模块表示职责，不表示具体芯片布局；缓存策略、流水线数量与专用指令支持随架构变化。主机搬运部分以具有独立显存的 GPU 为基础。

2.1 从就绪指令到运算结果

问题：Warp 被选中之后，谁来完成加法？

Warp 是线程的执行分组，不是加法器。调度器选出可发射指令后，相关执行流水线处理活跃线程的操作数。以 y[i] = x[i] + z[i] 为例，逻辑过程包括加载、加法和存储；源码中的一行不等于一条机器指令。

背景与机制：不同指令使用不同执行资源

执行资源的功能分工
资源典型任务理解要点
整数／浮点流水线地址运算、整数加法、浮点乘加不同类型的指令吞吐与延迟可以不同
加载／存储单元形成访存请求，传递加载结果它连接线程执行与存储系统，不是显存本身
特殊函数资源部分数学函数或近似运算并非所有数学函数都由一条专用指令完成
Tensor Core 等矩阵运算资源受支持形状与数据类型的矩阵乘加需要相应指令或库；普通标量加法不会自动成为矩阵运算

与 CPU 流水线类似，延迟是某次操作产生结果需要的时间，吞吐量是单位时间能处理的工作量。一条指令尚未完成，流水线可能已接收其他独立工作；具体发射频率受架构与资源限制。

参考：Nsight Compute 硬件模型。这里的功能分类不表示每种指令都有完全独立的硬件。

整数与浮点在表示范围、舍入和运算语义上的系统对比，见 附录 14：整数与浮点运算。

计算类型决定可用资源

Transformer 的矩阵乘法可利用专用矩阵资源；Softmax、归一化、激活等还需要归约和逐元素计算。同一算子也可能同时使用多类资源。更低精度可能提高吞吐、减少搬运，但需验证误差与动态范围。

矩阵任务的自顶向下实现见 第四章；普通 FMA 与矩阵指令的差别、片段布局和使用条件集中在 附录 15；CPU/GPU 部件对照与电路见 附录 16。

2.2 操作数存放在哪里

问题：线程寄存器与设备内存为什么同时存在？

线程需要快速访问正在计算的少量数据，也需要处理远大于片上容量的数组。不同存储资源承担不同范围的数据保存任务。程序中的“谁可以访问”与硬件中的“数据放在哪里”是两个问题。

存储语义与物理实现分开理解
名称用途／访问范围容易混淆之处
寄存器每线程的工作值，通常由编译器分配逻辑上独立，物理上使用 SM 的寄存器资源
共享内存本章采用普通 Block 内共享的模型容量有限，协作读写需要正确同步
全局内存可被不同线程访问的设备数据一次全局访问可命中缓存，不等于每次都访问 DRAM
Local Memory线程私有的内存空间，可承载寄存器溢出或部分局部数组“私有”描述访问语义，不保证位于片上；可经缓存访问设备内存

核心关系：寄存器与共享内存的用量影响一个 SM 能容纳多少驻留工作；显存容量决定能存放多少数据，不能直接代替 SM 的片上资源。分布式共享内存等新特性不在本节展开。

参考：CUDA 高级核函数编程：存储空间与硬件多线程。

2.3 连续读取与分散读取：访存合并

上一节说明数据存放在哪里。本节讨论数据如何从存储系统送到线程：即使读取的数据量相同，线程所需数据在内存中的分布，也会影响存储系统的工作量。

问题：32 个线程各读一个数，连续取数与间隔取数有何不同？

考虑同一 Warp 的 32 个活跃线程执行同一条全局加载指令。用 lane 表示线程在 Warp 内的编号 0–31，数组 x 的每个元素占 4 字节：

v = x[lane];      // T0 读 x[0]，T1 读 x[1]，T2 读 x[2]，……
v = x[8 * lane];  // T0 读 x[0]，T1 读 x[8]，T2 读 x[16]，……

这是两种待比较的取数方式，不是连续执行的两行程序。两者都需要 32 个数，即 128 字节；区别在于第一种地址相邻，第二种相邻线程的地址相差 32 字节。

背景：线程需要一个元素，存储系统按地址区域组织访问

x[i] 对应地址 数组基址 + 4 × i。线程的加载给出所需地址和数据大小；访存请求则是执行侧向缓存／存储系统发出的取数请求。32 个线程的读取需求，并不必然变成 32 笔独立的 DRAM 访问。

这与 CPU 按缓存行组织数据访问有相近的背景：硬件处理数据时有自己的粒度，而非只按源代码中的变量大小处理。本节按 32 字节的对齐地址段统计全局加载，每段可容纳 8 个 4 字节元素；这里的 32 字节段不等同于完整缓存行，也不是对 DRAM 内部访问粒度的规定。

机制：将同一条加载指令的地址按所在段归并

硬件根据该 Warp 各活跃线程的地址，组织覆盖所需数据的内存事务，这称为访存合并（coalescing）。例如，基址对齐时，T0–T7 读取的 x[0]–x[7] 都落在同一段，可合在该段的一次取数中；返回后，各线程仍得到自己所需的元素。若它们分别读 x[0]、x[8]、x[16]…，这些地址落在不同段，就需要覆盖更多段。

核心内容：读取量相同，不代表请求覆盖量相同

本例连续且对齐时覆盖 4 段，大步长时覆盖 32 段，线程实际需要的数据始终是 128 字节。因此，算子优化除了考虑“每个线程算什么”，还要考虑同一 Warp 的线程在同一次加载中读哪些地址。地址合并良好通常有利于数据供给，但不能据此直接推断运行时间相差多少倍。

合并组织的是地址请求，不会重新划分 Warp，也不提供额外原子性。实验采用 CUDA Best Practices：全局访问合并 中计算能力 6.0 及以上的 32 字节事务模型，并限定每线程读取一个 4 字节值；不推广到所有指令与 GPU。下一节进一步讨论：数据取来以后，如何减少重复读取。

2.4 复用数据与块内协作

问题：同一份数据需要多次计算，是否每次都重新加载？

寄存器适合保留线程自己的中间结果；多个线程需要共同使用一块数据时，可以把数据分块载入共享内存，再进行多次运算。这种分块组织称为 tiling。缓存可能自动保留数据，共享内存则由程序显式安排读写。

共享内存分成多个 bank，以支持并行访问。请求中的不同地址若争用同一 bank，可能需要分步处理；对同一位置的读取可使用广播。bank 冲突是资源争用，数据竞争是缺少正确同步的冲突访问，两者不能等同。

核心关系：复用可能减少反复加载，但增加共享内存占用、指令与同步成本。对只使用一次的数据，额外搬入共享内存未必有收益。

参考：共享内存与 bank；异步块内搬运另见 CUDA 异步数据复制。

2.5 从主机内存到 GPU 数据路径

问题：CPU 中的数组怎样成为 GPU 的操作数？

对具有独立显存的 GPU，主机内存与设备内存是不同的物理资源。一次显式复制把数据送到设备可用的位置；之后，GPU 内部的加载指令才为线程获取操作数。两种搬运发生在不同层次。

设备上的复制引擎与 SM 计算资源可以承担不同任务，但传输与计算能否交叠取决于硬件能力、缓冲区、操作依赖和提交方式。常见异步主机传输使用页锁定（pinned）内存；它仍然是主机内存，不会因页被锁定就变成显存。

多个计算如何连接？

Kernel 是计算代码，一次 Kernel 启动是一项工作；Stream 是组织操作顺序的对象。例如同一 Stream 可以安排“复制输入 → 启动 Kernel A → 启动 Kernel B → 复制输出”。A、B 之间的数据留在设备上，就不必为这一步依赖往返主机。

统一虚拟地址与统一内存也不意味着搬运成本消失：地址命名、访问权限、物理位置和数据迁移是不同层次。统一内存可由系统管理迁移或远程访问，具体行为取决于平台。

核心关系：设备内部带宽与主机互连带宽是不同预算；计算本身很快，也可能被输入、输出搬运拖慢。第三章将解释提交、依赖与完成确认。

参考：统一内存、地址空间与页锁定内存、异步执行与 Stream。

2.6 计算能力与数据供给如何共同限制性能

问题：为什么更多计算单元不一定缩短时间？

只有取得操作数，算术资源才能工作。算术强度 I 表示每搬运一字节数据完成多少浮点运算，单位为 FLOP/byte；必须说明在哪个存储边界统计字节。本节选设备 DRAM 边界。

教学示例：假设 P = 10 TFLOP/s、B = 1 TB/s，若 I = 2 FLOP/byte，带宽侧给出 2 TFLOP/s 的上限；若通过复用将 I 提高到 20，上限由计算侧的 10 TFLOP/s 约束。数字仅用于说明量纲，不对应某款 GPU。

不同现象对应不同检查方向
现象可能需要检查
运算资源等待数据依赖链、缓存命中、可就绪工作量
DRAM 接口忙碌而计算未满有效数据比例、地址合并与数据复用
Kernel 很短但整体耗时高主机搬运、提交与同步开销

核心关系：延迟隐藏增加等待期间可做的工作；复用减少所需数据搬运；合并提高请求对有效数据的覆盖。它们针对不同问题，最终应通过测量判断瓶颈。

参考：Nsight Compute：Roofline 图与性能分析。
