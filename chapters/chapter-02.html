第三章 · 软件与硬件的连接

从驱动到硬件执行

本章只回答软件边界：资源如何描述，Kernel 如何提交，何时能够使用结果。执行流水线与存储细节沿用前两章；API 代码按需查附录。

范围：以 NVIDIA CUDA 与 Linux 驱动分层为例，讨论普通主机端 kernel 启动；不展开图形渲染、MIG、MPS 和设备端启动。流程图表示职责与先后依赖，不表示固定的系统调用次数或芯片内部协议。

3.1 软件眼中的 GPU 是什么

问题：一段 CPU 程序如何使用另一套执行资源？

CPU 正在执行主机程序，GPU 的 SM 则执行另一种机器指令。调用 GPU 计算需要同时解决三个问题：设备能够访问哪些数据、执行哪份设备代码、何时可以使用计算结果。

在本章的计算模型中，可以将 GPU 理解为由驱动管理、具有可查询能力与内存资源、接受工作提交并报告完成状态的计算设备。这是软件接口层面的描述；第一章中的 SM、寄存器文件和执行流水线，是实现这些能力的硬件。

同一设备的两个观察角度
程序可描述或查询的内容硬件承担的工作
设备编号、计算能力、资源上限具体 GPU 的指令能力与资源配置
设备可访问的内存地址与分配地址转换、缓存和存储系统完成访问
核函数、参数、Grid / Block 尺寸安排线程块，在 SM 内执行线程指令
Stream 顺序、事件与同步遵守依赖、执行工作并使完成状态可被观察

GPU 设备句柄不等于一个 SM；设备指针也不表示程序直接获得了某个显存芯片的物理地址。CUDA 能力与软件组件参见 CUDA 平台说明。

3.2 运行时、用户态驱动与内核态驱动

背景：编程接口与操作系统中的设备管理分属不同层次

cudaMalloc 和核函数启动语法属于常用的 CUDA Runtime 层。Runtime 利用更低层的 CUDA Driver API；后者虽然带有“Driver”一词，应用调用它时仍从 CPU 用户态开始，并非直接执行操作系统内核代码。

内核态驱动使多个应用可以受控地使用同一设备；部分设备管理也可能由 GPU 上的固件承担。一次工作获得执行机会之后，SM 内每次选择哪个就绪 Warp，属于硬件调度。驱动通常不在 CPU 上逐条挑选 Warp 指令。

CUDA 核函数中的“核”与操作系统内核不是同一概念。NVIDIA 的 开放内核模块仓库只覆盖软件栈的一部分，并要求匹配的用户态组件与 GSP 固件；不能据此将整个 CUDA 驱动栈视为同一份开放源码。API 分层见 Runtime 与 Driver API 的区别。

3.3 驱动接口如何表示一次计算

底层逻辑：用软件对象描述资源归属与执行依赖

一段核函数代码本身不足以启动计算。驱动还需知道它在哪个设备环境中执行、参数中的地址属于哪些资源，以及它与其他工作有什么顺序关系。Driver API 将这些信息分为可操作的对象。

从应用对象到设备工作
对象含义与作用与第一章的区别
Device / CUdevice标识一个可用 CUDA 设备并查询其属性不是一个线程或 SM
Context / CUcontext与设备关联的 CUDA 执行环境，管理相关资源与状态不是某个 Warp 的寄存器上下文，也不表示独占设备
Module / Function已加载的设备代码模块及其中的核函数入口表示代码，不是已经创建的一批线程
设备内存分配保存输入、输出等数据，提供设备可访问的地址不等于 SM 为线程分配的寄存器或块级共享内存
Stream / CUstream表达一系列操作的执行顺序不是一条物理流水线，也不固定绑定某个 SM
Event / CUevent在 Stream 中标记进度，用于查询、等待或计时观察完成关系，不指定 Warp 的发射顺序

Runtime 通常为每个进程所使用的设备使用 primary context；应用也可通过 Driver API 显式管理上下文。上下文描述应用使用设备的环境，驻留描述线程状态已占用 SM 资源。上下文存在时，设备可以暂时没有任何正在执行的核函数。

GPU 使用虚拟地址及相应映射完成内存访问。本章的 cudaMalloc 示例采用显式设备分配：CPU 不能把返回的设备指针当作普通主机数组直接解引用。统一地址空间也不意味着所有内存都具有相同的可访问性、位置或访问成本。

参考：上下文管理、Stream API、CUDA 内存模型。线程驻留状态另见 附录 6。

3.4 从一段 CUDA 代码到一次启动请求

示例：将 100 个整数分别加一

设 add_one 对每个有效数组元素加一，越界线程不写输出。主机负责准备资源和提交工作，GPU 执行计算；两者通过依赖与完成状态连接。

// 数据资源已准备好：本例只突出提交顺序
复制输入到设备
add_one<<<2, 64>>>(d_in, d_out, 100);
等待设备完成
复制输出到主机

这是流程伪代码。资源申请、释放与 Driver API 参数写法见 附录 8.5。

编译时，主机部分成为 CPU 代码；核函数成为设备代码，常以 cubin 和／或 PTX 包装在程序中。加载时使用适合设备的机器码，必要时由 JIT 将 PTX 转换为机器码。这里执行 100 次加一并不需要传输 100 份函数代码；每个线程运行同一份代码，使用各自的索引及数据。编译产物详见 附录 8.2。

3.5 启动请求如何到达 SM

问题：启动语句已经返回，GPU 发生了什么？

一次启动描述“哪个入口、哪些参数、多少线程、属于哪个 Stream”。驱动软件栈将工作组织为设备可处理的提交信息。提交机制可使用命令缓冲区、队列及通知机制；这里的命令是启动或传输等工作描述，不是核函数内部每一条算术机器指令。

一次启动的资源引用见图 3-2；线程数量与 Warp 划分见下方配置实验；CPU 与 GPU 的完成关系见 3.7。驱动提交与 SM 内部的 Warp 指令发射属于不同尺度。

在 第一章 1.4 中，一个 Warp 等待内存结果时，其他就绪 Warp 可以利用执行机会。这里切换的是已驻留工作中的指令来源：其状态已在 SM 内，通常无需 CPU 驱动保存和恢复整个线程上下文。设备抢占或不同应用环境之间的切换则属于另一层问题。

此流程为教学归纳，并非 NVIDIA 私有命令格式的逐字段描述。硬件执行依据见 硬件多线程与 SIMT 执行。

3.6 代码、启动配置与硬件资源的对应关系

n = 100 描述有效数据量，Block 大小描述线程如何分组。每个 Block 内按线性线程编号组成 Warp；不足 32 个线程的 Warp 有空余 lane。线程存在但索引越界，与线程根本不存在，是两种不同情况。

程序表达执行含义与第一章的联系
blockIdx / threadIdx区分逻辑执行实例；不是物理核心编号线程状态与硬件资源分离
input[i]线程计算地址，加载指令经访存系统获取数据缓存与数据等待决定指令何时就绪

if (i < n)仅满足条件的线程写入结果参与掩码、条件执行与通道利用率

改变 Block 大小会改变每块线程数、块级协作范围和资源需求。实际驻留数量还取决于编译器分配的寄存器、共享内存用量及硬件上限。因此，启动更多线程与增加物理执行资源不是同一件事，Block 越大也不保证运行越快。

3.7 提交、执行与完成的区别

主机和 GPU 可以各自推进。启动调用返回通常只表示 CPU 已完成相应的启动操作，不表示输出已经算好。同一普通 Stream 内的操作按提交顺序执行；不同 Stream 之间若有数据依赖，应显式表达，而不能根据 CPU 提交语句的先后推断设备一定已经完成。

Stream 是软件中的顺序抽象，硬件队列是实现提交的机制，执行引擎是实际做工作的资源。三者不存在普遍的一一对应关系；建立多个 Stream 只是表达潜在并发，不能保证设备同时执行这些工作。

参考：CUDA 异步执行与 Stream 顺序。

3.8 核心关系与自检

应用描述计算与依赖，编译器生成设备指令，运行时与驱动建立资源并提交工作，GPU 硬件安排 Block 并执行 Warp 指令。这几个层次共同完成一次计算，但各自处理的对象与时间尺度不同。

启动 128 个线程，是否要求驱动创建 128 个 OS 线程？

不要求。GPU 线程是核函数的逻辑执行实例，其执行状态由 GPU 的相关资源承载。CPU 提交的是一项带有线程配置的工作。

一个 Stream 是否对应一个 SM？

不对应。Stream 表达操作顺序，一个核函数的多个 Block 可以在多个 SM 上执行。普通启动并不指定 Block 的具体 SM。

驱动上下文与驻留 Warp 的上下文是否相同？

不同。前者是 CUDA 执行环境及资源管理层次，后者是线程执行过程中保留的数据和控制状态。普通驻留 Warp 之间的指令调度无需逐次请求 CPU 驱动进行 OS 式切换。
